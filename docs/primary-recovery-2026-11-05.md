## 1. 故障证据

2026-11-05（北京时间）排查第一套：Web 5177、原生服务端 18080、MySQL 容器均运行，列表查询可用，数据库模式为 MySQL，磁盘约 50%。但是原生服务进程没有到上游 `139.196.171.27:7190` 的连接，真实 `/System/LogIn` 请求在约 30 秒后返回 `success=true,data=false`，提示“服务器响应超时”。不能仅凭 HTTP 200、容器 Up、缓存账号信息或 `/health` 就认定消息业务正常。

第一套原生日志 11/3 反复出现重新登录失败、强制下线。排查时 10/26 周表最后记录为 11/1 21:51:59；11/2 周表只有两条 11/3 的 source=2 记录。自动登录状态文件仍停在 11/1，已经失去时效。

本次确认不是 SQLite 回退，也不是数据库查询失效。上游为何最初强制下线仍需与原生服务/供应商进一步核实；本次修复的是恢复链路卡死及当前离线状态。

## 2. 自动恢复为何停摆

`docker-control/autologin.pause` 内容为 `reload database configuration`，11/1 由自动数据库配置恢复流程写入。对应的完成标记为 `autologin-1793541316-1`。

旧脚本用 shell 内存变量 `managed_restart=1` 区分自动恢复与手动暂停。11/2 容器重启后该变量变回 0，持久化的暂停文件却仍存在，于是脚本一直进入“被退出 API 暂停”的等待分支。它不再重试登录，也不更新状态文件。

此外，旧超时恢复条件要求暂停文件不存在；即使恢复任务仍拥有这个暂停文件，连续超时也无法触发下一步有上限的进程恢复。

## 3. 修复及操作范围

- `ops/fnos-youchat-service/autologin-observability.sh` 增加自动暂停归属判断：已知自动恢复原因、对应 autologin 完成记录、且无待执行重启请求，才允许接续中断的恢复。任意手动暂停、来源不明或仍待执行的恢复不会自动解除。
- 接续自动恢复时强制本次启动采用 `keep`，避免重复执行数据库切换流程；运行时 MySQL 连通性检查仍保留。
- 已恢复归属的自动任务允许进入现有超时恢复规则：连续三次上游超时、上游 TCP 可达、15 分钟冷却、成功前最多两次。手动暂停若在恢复期间到来仍会阻止后续重试，不会在登录成功时误删。
- 真正等待手动暂停时持续写 `status=paused` 及检查时间，避免留下几天前的超时状态。
- `scripts/install-fnos-login-health.py` 新增 `--stack primary|secondary|all`，默认行为仍为两套，可独立修复第一套。

本次仅执行 `--stack primary`：安装脚本备份旧原文件，只重启第一套 autologin sidecar。确认第一套仍有真实上游登录超时后，通过既有进程监督器发起一次原生进程恢复，任务 ID 为 `autologin-1793808952-primary-repair`。没有重启 MySQL、第一套 Web 或第二套服务，也没有修改数据库模式、历史数据或账号凭证。

操作前完整读取并校验最近云盘 gzip 备份：`youchat-1556504756803862529-20261104-033011.sql.gz`，压缩 96,211,815 字节、解压 SQL 365,764,584 字节。使用原云盘路径，没有迁移数据目录。
